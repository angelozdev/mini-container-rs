**Al terminar:** tu programa lanza un comando con su propio nombre de máquina, y la máquina de verdad no se entera.

El *hostname* es el nombre de la máquina. El comando `hostname` lo imprime. El kernel guarda ese nombre en una lista, y todos los procesos de la máquina leen la misma.

Hoy tu programa le pide al kernel su propia copia de esa lista. Escribe un nombre nuevo en la copia y lanza un comando que lee la copia.

Un *namespace* es una copia privada de una lista del kernel. El tipo de namespace que guarda el hostname se llama *UTS*. Es solo un nombre técnico: no hace falta que recuerdes qué significa la sigla.

<Aside type="note" title="Analogía">
Un edificio tiene un letrero en la entrada con su nombre. La recepcionista le entrega a tu programa una fotocopia del letrero. Tu programa tacha el nombre en su fotocopia y escribe otro. El letrero de la entrada sigue igual.
</Aside>

El letrero es el hostname. La recepcionista es el kernel. La fotocopia es el namespace UTS.

## Qué vas a escribir

Un archivo nuevo y tres cambios:

1. `Cargo.toml` gana una dependencia, `nix`.
2. `src/namespaces.rs` es el archivo nuevo. Es el único que habla con el kernel.
3. `src/container.rs` llama a `namespaces` antes de lanzar el programa.
4. `src/main.rs` declara el módulo nuevo.

Un programa le pide cosas al kernel con *llamadas al sistema*. Una llamada al sistema es un pedido que el programa le hace al kernel: abrir un archivo, lanzar un proceso o cambiar el hostname. Hoy usas dos:

- `unshare`: «dame una copia privada de esta lista».
- `sethostname`: «cambia el nombre que dice la lista». Escribe en la lista UTS del proceso que la llama.

No las llamas a mano: el crate `nix` las ofrece como funciones de Rust. Con `nix`, tu código no necesita `unsafe`, la marca con la que Rust avisa «aquí el compilador no puede comprobar esto».

Teclea cada trozo, como en 1a. El código y los textos que imprime van en inglés. La página te explica en español qué dice cada texto la primera vez que aparece.

Antes de escribir, una predicción.

1. **Añade el crate `nix`.**

   - `sched`: trae `unshare`.
   - `hostname`: trae `sethostname`.

   Estando en la raíz del repo, en Linux:


   - `--features sched,hostname`: las dos features, separadas por una coma y sin espacios.
   - Efecto: escribe una línea en `Cargo.toml`. Todavía no descarga el crate.

2. **Pide la copia: `src/namespaces.rs`.**

   En Zed, crea el archivo `src/namespaces.rs`. Empieza por lo que necesita traer:

   ```rust title="src/namespaces.rs"
   use anyhow::{Context, Result};
   use nix::sched::{CloneFlags, unshare};
   ```

   - `anyhow::{Context, Result}`: lo mismo que en `container.rs`. `Result` es el resultado de algo que puede fallar, y `Context` añade un mensaje al error.
   - `nix::sched`: el módulo de `nix` donde vive `unshare`.
   - `CloneFlags`: un conjunto de banderas. Una *bandera* es una opción que se enciende o se apaga. Hay una por cada tipo de namespace.
   - `unshare`: la función que le pide al kernel la copia.

   Debajo de los `use`, deja una línea en blanco y escribe la función:

   ```rust title="src/namespaces.rs"
   pub fn unshare_namespaces() -> Result<()> {
       unshare(CloneFlags::CLONE_NEWUTS)
           .context("could not create the namespaces: did you run it with sudo?")
   }
   ```

   - `pub fn unshare_namespaces()`: una función pública, para llamarla desde `container.rs`. Se llama «namespaces», en plural, porque más adelante pedirá más tipos de copia.
   - `-> Result<()>`: puede fallar. El `()` es «nada»: si sale bien, no devuelve ningún dato.
   - `CloneFlags::CLONE_NEWUTS`: la bandera que dice «quiero una copia privada de la lista del hostname». `NEWUTS` significa «UTS nuevo».
   - `unshare(...)`: le pide al kernel lo que dice la bandera. Tu propio proceso, `mini-container`, pasa a usar la copia. Los procesos que lance después nacen dentro de ella.
   - `.context("...")`: si el kernel dijo que no, pone este mensaje delante del error. El texto dice «no pude crear los namespaces: ¿ejecutaste con sudo?». La causa original queda debajo.
   - No hay `;` al final: esa expresión es el valor que devuelve la función. Devuelve el `Result` tal cual, sin `?` ni `Ok(())`.

4. **Escribe el nombre en tu copia.**

   Vuelve a `src/namespaces.rs`. Arriba hacen falta dos líneas nuevas: la función que escribe el hostname y el nombre que va a escribir.

   ```rust title="src/namespaces.rs" ins={3,5}
   use anyhow::{Context, Result};
   use nix::sched::{CloneFlags, unshare};
   use nix::unistd::sethostname;

   pub const HOSTNAME: &str = "container";
   ```

   - `use nix::unistd::sethostname;`: `unistd` es el módulo de `nix` con las llamadas básicas de Unix. `sethostname` vive ahí.
   - `pub const HOSTNAME: &str = "container";`: el nombre fijo que le pondrás a la copia. `pub` para usarlo desde `container.rs`. Una constante en inglés, como todo el código.

   ```rust title="src/namespaces.rs" ins={5-8}

       unshare(CloneFlags::CLONE_NEWUTS)
           .context("could not create the namespaces: did you run it with sudo?")

   pub fn set_hostname(name: &str) -> Result<()> {
       sethostname(name).context("could not set the hostname")
   ```

## El error que explica qué falta

Ese error dice primero qué intentaba tu programa y después la causa. No tenía por qué ser así. Un `Result` se puede abrir con `.unwrap()`: si hubo un error, el programa se cae con un *panic*. Un panic es una caída: Rust imprime dónde pasó y sale con el código 101.

Mira la función `unshare_namespaces` escrita de las dos formas, y lo que ve quien corre el programa sin `sudo`. La izquierda es tu función con `.unwrap()` en vez de `.context(...)`. Como `.unwrap()` ya abre el `Result`, la función termina con `Ok(())`. No hace falta que lo pruebes: la salida de la izquierda es la de tu `src/namespaces.rs` con ese cambio, compilado y corrido sin `sudo`.

### 2a.1 El hostname desde una variable de entorno

**Objetivo:** el hostname sale de la variable de entorno `MINI_CONTAINER_HOSTNAME`. Si la variable no existe, sigue siendo `container`.

Una *variable de entorno* es un nombre con un valor que un programa recibe de quien lo lanza. Se escribe `NOMBRE=valor`.

Un detalle de `sudo`: antes de lanzar tu programa, borra casi todas las variables de tu terminal. Las que escribes después de `sudo`, en el mismo comando, sí las deja pasar. Por eso el resultado esperado pone la variable después de `sudo`.

```sh title="Resultado esperado"
$ sudo MINI_CONTAINER_HOSTNAME=api ./target/debug/mini-container run /bin/hostname
api
$ sudo ./target/debug/mini-container run /bin/hostname
container
```

Si pones la variable antes de `sudo`, como en `MINI_CONTAINER_HOSTNAME=api sudo ./target/debug/mini-container run /bin/hostname`, `sudo` la borra y tu programa imprime `container`. Eso no es un fallo de tu código.

<Hint n={1}>`std::env::var` lee una variable de entorno. Mira qué devuelve: no es un `String` a secas. Devuelve un `Result`, y es un `Err` cuando la variable no existe.</Hint>

<Hint n={2}>Cuando la variable no existe, quieres usar `HOSTNAME`. `.unwrap_or_else(...)` recibe una función que arma el valor por defecto solo si hubo un error. `HOSTNAME` es un `&str` y `env::var` entrega un `String`: `.to_string()` los iguala.</Hint>

<Hint n={3}>Hazlo en una función pequeña de `namespaces.rs` que devuelva el nombre. Después cambia el argumento de `set_hostname` en `run`. `set_hostname` pide un `&str`: a un `String` se le antepone `&`.</Hint>

## Fuentes
