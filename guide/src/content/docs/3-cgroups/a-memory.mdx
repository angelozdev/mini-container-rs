**Al terminar:** el comando que lanza tu programa no puede usar más de 50 MB de <Term id="ram">RAM</Term>. Si lo intenta, el <Term id="kernel">kernel</Term> lo mata y tu programa lo dice.

La *RAM* es la memoria rápida de la máquina. Los <Term id="process">procesos</Term> guardan ahí sus datos mientras corren.

Hasta hoy, el comando usa toda la RAM que quiera. Si tiene un error y no deja de pedir memoria, deja sin ella a los demás procesos de la máquina. Es el «vecino ruidoso» de la lección.

Hoy le pones un tope. No lo hace cumplir tu programa: lo hace cumplir el kernel. Para pedírselo usas un <Term id="cgroup">cgroup</Term>.

Un *cgroup* es una función del kernel que limita lo que un grupo de procesos puede gastar. Se maneja con carpetas y archivos dentro de `/sys/fs/cgroup`. El grupo es el comando y todo lo que él lance.

El diagrama muestra la RAM como la tienes hoy y con un cgroup.

## Qué vas a escribir

Un archivo nuevo y cuatro cambios:

1. `src/cgroup.rs` es el archivo nuevo. El tipo `Cgroup` crea la carpeta, escribe los topes, lee cuántas veces mató el kernel y la borra al final.
2. `src/cli.rs`: el hijo recibe también la ruta del cgroup.
3. `src/namespaces.rs`: una función nueva, para que el hijo tenga su propia copia de los <Term id="mount">montajes</Term>.
4. `src/container.rs`: `run` crea el cgroup y avisa si el kernel mató algo. `init` entra en él.
5. `src/main.rs`: declara el módulo nuevo y pasa la ruta al hijo.

`Cargo.toml` no cambia: no hace falta ninguna <Term id="feature">feature</Term> nueva.

Teclea cada trozo, como en 2c. El código y los textos que imprime van en inglés. La página te explica en español qué dice cada texto la primera vez que aparece.

Antes de escribir, una predicción. Un dato para responderla: el cgroup tendrá dos topes. `memory.max` limita la RAM. `memory.swap.max` limita el <Term id="swap">swap</Term>. El *swap* es espacio en disco, o en una zona comprimida de la memoria, donde el kernel guarda datos de la RAM cuando se llena. Con `0`, el cgroup no puede usarlo.

<QuizOption>Le da la memoria que pide: 200 MB caben en la RAM libre de la máquina.<Fragment slot="feedback">El tope no mira cuánta RAM libre hay. Mira lo que gasta el cgroup. ## Los trozos

<Steps>

1. **Declara el módulo y escribe lo de arriba.**

   En `src/main.rs`, añade una línea al principio:

   ```rust title="src/main.rs" ins={1}
   mod cgroup;
   mod cli;
   mod container;
   mod filesystem;
   mod namespaces;
   ```

   - `mod cgroup;`: declara el módulo nuevo. Rust lo busca en `src/cgroup.rs`.

   Crea el archivo `src/cgroup.rs` y escribe lo de arriba:

   ```rust title="src/cgroup.rs" ins={1-11}
   use std::fs;
   use std::path::{Path, PathBuf};

   use anyhow::{Context, Result};

   const CGROUP_ROOT: &str = "/sys/fs/cgroup";
   pub const MEMORY_MAX: &str = "50M";

   pub struct Cgroup {
       path: PathBuf,
   }
   ```

   - `std::fs`: el módulo de Rust para archivos. Crear una carpeta o escribir un archivo son funciones suyas. Con eso se maneja un cgroup.
   - `Path` y `PathBuf`: los dos tipos de ruta de Rust. `PathBuf` es dueño de su ruta, como `String`. `Path` la presta, como `&str`.
   - `anyhow::{Context, Result}`: lo mismo que en los otros archivos.
   - `CGROUP_ROOT`: la carpeta donde viven los cgroups. No lleva `pub`: solo este archivo la usa.
   - `MEMORY_MAX`: el tope, `50M`. La `M` es de megabytes. El kernel lo guarda en bytes: 50 por 1024 por 1024, o sea 52428800. Lleva `pub` porque `container.rs` la usa.
   - `pub struct Cgroup { path: PathBuf }`: el tipo que representa un cgroup. Guarda solo su ruta. El campo no es `pub`: fuera de este archivo nadie puede armar un `Cgroup` a mano. Hay que pasar por `create`.

2. **Crea la carpeta.**

   Un cgroup nace cuando creas una carpeta dentro de `/sys/fs/cgroup`. Debajo de `struct Cgroup`, con una línea en blanco:

   ```rust title="src/cgroup.rs" ins={1-11}
   impl Cgroup {
       pub fn create(name: &str) -> Result<Self> {
           let path = Path::new(CGROUP_ROOT).join(name);
           fs::create_dir(&path)
               .with_context(|| format!("could not create the cgroup {}", path.display()))?;
           Ok(Self { path })
       }

       pub fn path(&self) -> &Path {
           &self.path
       }
   ```

   - `impl Cgroup {`: el bloque donde van las funciones del tipo. No lo cierres todavía: las funciones de los pasos 3 y 4 van dentro. Lo cierras en el paso 4.
   - `create(name: &str) -> Result<Self>`: `Self` es `Cgroup`. Devuelve un `Cgroup` o un error.
   - `Path::new(CGROUP_ROOT).join(name)`: la ruta de la carpeta nueva, `/sys/fs/cgroup/<name>`.
   - `fs::create_dir(&path)`: crea la carpeta. Falla si ya existe o si no tienes permisos.
   - `.with_context(|| format!(...))?`: si falla, el error dice «no pude crear el cgroup» y la ruta. Como en 2c, la <Term id="closure">closure</Term> arma el mensaje solo si hubo error.
   - `Ok(Self { path })`: devuelve el `Cgroup`. Escribir solo `path` es lo mismo que `path: path`.
   - `path(&self) -> &Path`: devuelve la ruta prestada. `&self` es «este cgroup, prestado». `run` la usa para decirle al hijo dónde está el cgroup.

3. **Escribe los topes: `limit_memory`.**

   Poner un tope es escribir un número en un archivo de la carpeta. Hoy escribes en dos archivos.

   El primero es `memory.max`, el tope de RAM. Si el cgroup lo alcanza y el kernel no puede recuperar memoria, entra el <Term id="oom-killer">OOM killer</Term>. El *OOM killer* es la parte del kernel que mata un proceso cuando la memoria se acaba. «OOM» viene de «out of memory», sin memoria. Mata a un proceso del cgroup, y a ninguno de fuera.

   El segundo es `memory.swap.max`, el tope de swap que ya conoces. Con `0`, el cgroup no puede usarlo. Sin él, el comando se salvaría mandando datos allí, y el kernel no mataría a nadie. Lo ves más abajo, en la trampa.

   Debajo de `path`, con una línea en blanco:

   ```rust title="src/cgroup.rs" ins={1-4}
       pub fn limit_memory(&self, max: &str) -> Result<()> {
           self.write("memory.max", max)?;
           self.write("memory.swap.max", "0")
       }
   ```

   - `max: &str`: el tope, escrito como texto: `"50M"`.
   - `self.write("memory.max", max)?;`: escribe el tope en `memory.max`. `write` es una función tuya, del paso 4: escribe un texto en un archivo del cgroup. El `?` sale con el error si falla.
   - `self.write("memory.swap.max", "0")`: escribe `0` en `memory.swap.max`. Es lo último que hace la función, y devuelve su `Result` tal cual.

   Cada escritura sale de una de dos maneras. Mira la de `memory.max`:

   <CallOutcomes
     call='fs::write(&path, "50M")'
     ok="Ok(())"
     okNote="el kernel guarda el tope: 52428800"
     error="Err(EINVAL)"
     errorNote="el kernel no entiende el valor: sale con 1"
   />

   Con `50M`, el kernel guarda el tope en bytes. Con un valor que no entiende, como `50MB`, la escritura falla con el error 22, `EINVAL`: el código de error del sistema para «argumento inválido». Más abajo ves ese error en pantalla.

4. **Lee cuántas veces mató el kernel, y escribe `write`.**

   Cuando el kernel mata un proceso del cgroup, lo anota en `memory.events`. Es un archivo de texto con un contador por línea: el nombre, un espacio y un número. Así quedó en la máquina de pruebas, justo después de que el kernel matara al comando:

   ```text title="memory.events"
   low 0
   high 0
   max 53
   oom 1
   oom_kill 1
   oom_group_kill 0
   sock_throttled 0
   ```

   El que importa es `oom_kill`: el número de procesos del cgroup que mató un OOM killer. Los demás números cambian de una ejecución a otra.

   Debajo de `limit_memory`, con una línea en blanco:

   ```rust title="src/cgroup.rs" ins={1-13}
       pub fn oom_kills(&self) -> Result<u64> {
           let events_path = self.path.join("memory.events");
           let events = fs::read_to_string(&events_path)
               .with_context(|| format!("could not read {}", events_path.display()))?;
           parse_oom_kills(&events).context("memory.events has no oom_kill counter")
       }

       fn write(&self, file: &str, value: &str) -> Result<()> {
           let path = self.path.join(file);
           fs::write(&path, value)
               .with_context(|| format!("could not write {value} to {}", path.display()))
       }
   }
   ```

   - `oom_kills(&self) -> Result<u64>`: devuelve el contador, un entero sin signo de 64 bits, o un error.
   - `fs::read_to_string(&events_path)`: lee el archivo entero como texto.
   - `parse_oom_kills(&events)`: busca la línea `oom_kill` y devuelve `Option<u64>`: `Some(número)` o `None`. La escribes en el paso 6.
   - `.context("...")` sobre un `Option`: `anyhow` también lo permite. `Some(n)` pasa a `Ok(n)`, y `None` pasa a un error con ese mensaje.
   - `fn write(...)`: sin `pub`, solo `Cgroup` la usa. `self.path.join(file)` arma la ruta del archivo, y `fs::write(&path, value)` escribe el texto en él, en lugar de lo que hubiera.
   - `{value}`: un <Term id="placeholder">hueco</Term> con nombre. Rust pone ahí el valor de la variable `value`. El otro `{}` se rellena con `path.display()`.
   - El último `}` cierra el `impl Cgroup` que dejaste abierto.

5. **Borra al terminar: `Drop`.**

   Cada ejecución crea una carpeta. Si nadie la borra, se acumulan. Rust tiene un sitio para esto: el <Term id="trait">trait</Term> `Drop`. Un *trait* es una capacidad que un tipo puede tener. `Drop` dice qué hacer cuando un valor deja de usarse. Es su <Term id="destructor">destructor</Term>: el código que Rust ejecuta para limpiar cuando algo deja de usarse.

   Rust lo llama solo, al final del bloque donde vive el valor. También si el bloque sale antes por un error. Es una limpieza automática.

   Debajo del `impl Cgroup`, con una línea en blanco:

   ```rust title="src/cgroup.rs" ins={1-10}
   impl Drop for Cgroup {
       fn drop(&mut self) {
           if let Err(error) = fs::remove_dir(&self.path) {
               eprintln!(
                   "could not remove the cgroup {}: {error}",
                   self.path.display()
               );
           }
       }
   }
   ```

   - `impl Drop for Cgroup`: «`Cgroup` sabe limpiarse».
   - `fn drop(&mut self)`: la función que Rust llama. `&mut self` es «este cgroup, prestado para cambiarlo». No devuelve nada: un `drop` no puede devolver un error.
   - `fs::remove_dir(&self.path)`: borra la carpeta. Es `remove_dir`, no `remove_dir_all`: los archivos del cgroup los pone y los quita el kernel. Un cgroup solo se borra si está vacío, sin procesos dentro. Cuando `run` termina, el comando ya terminó, y el cgroup está vacío.
   - `if let Err(error) = ...`: «si el borrado falló, haz esto». Si salió bien, no hace nada.
   - `eprintln!(...)`: avisa por <Term id="stderr">stderr</Term> y dice qué carpeta no se pudo borrar. Como `drop` no puede devolver un error, avisar es lo único que puede hacer.

6. **Entra en el cgroup, y lee el contador.**

   Dos funciones sueltas, sin `impl`. Debajo de `impl Drop`, con una línea en blanco:

   ```rust title="src/cgroup.rs" ins={1-11}
   pub fn join(path: &Path) -> Result<()> {
       let procs = path.join("cgroup.procs");
       fs::write(&procs, std::process::id().to_string())
           .with_context(|| format!("could not join the cgroup {}", path.display()))
   }

   fn parse_oom_kills(events: &str) -> Option<u64> {
       events
           .lines()
           .find_map(|line| line.strip_prefix("oom_kill ")?.parse().ok())
   }
   ```

   - `join(path: &Path)`: la usa el hijo. Es una función suelta, no un método, porque el hijo no tiene un `Cgroup`: tiene solo la ruta que recibió.
   - `path.join("cgroup.procs")`: la ruta del archivo `cgroup.procs`.
   - `std::process::id().to_string()`: el <Term id="pid">PID</Term> del proceso que corre este código, hecho texto. Escribirlo en `cgroup.procs` mueve ese proceso al cgroup.
   - En el hijo ese PID es el 1: es el primero de su lista de procesos nueva, como viste en 2b. Funciona igual. Desde fuera, `cgroup.procs` muestra el PID que tiene en tu máquina.
   - `events.lines()`: recorre el texto línea por línea.
   - `.find_map(|line| ...)`: prueba la closure con cada línea y devuelve el primer resultado que sea `Some`.
   - `line.strip_prefix("oom_kill ")`: si la línea empieza por `oom_kill ` con su espacio, devuelve lo que sigue: el número, todavía como texto. Si no, devuelve `None`. El espacio importa: `oom_group_kill 0` no empieza por `oom_kill `.
   - `?` dentro de la closure: si es `None`, la closure devuelve `None` en el acto.
   - `.parse().ok()`: convierte el texto en número. Rust sabe que es un `u64` por el tipo que devuelve la función. `.ok()` convierte un error en `None`.

7. **El hijo recibe la ruta: `cli.rs`.**

   El hijo es tu programa lanzado con `child` delante. Hasta hoy recibía `child /bin/ps -o pid,comm`. Hoy recibe también la ruta del cgroup: `child /sys/fs/cgroup/mini-container-4172 /bin/ps -o pid,comm`.

   En `src/cli.rs`, añade una línea al principio:

   ```rust title="src/cli.rs" ins={1}
   use std::path::PathBuf;
   ```

   Cambia la variante `Child`. Ahora lleva dos datos con nombre:

   ```rust title="src/cli.rs" del={4} ins={5-8}
   #[derive(Debug, PartialEq, Eq)]
   pub enum Invocation {
       Run(CommandLine),
       Child(CommandLine),
       Child {
           cgroup: PathBuf,
           command: CommandLine,
       },
   }
   ```

   Y cambia `parse`. Antes usaba `Invocation::Run` e `Invocation::Child` como funciones. `Child` ya no puede: tiene dos campos.

   ```rust title="src/cli.rs" del={3-12} ins={13-23}
   pub fn parse(args: impl IntoIterator<Item = String>) -> Option<Invocation> {
       let mut args = args.into_iter();
       let invocation = match args.next()?.as_str() {
           "run" => Invocation::Run,
           "child" => Invocation::Child,
           _ => return None,
       };
       let program = args.next()?;
       Some(invocation(CommandLine {
           program,
           args: args.collect(),
       }))
       match args.next()?.as_str() {
           "run" => Some(Invocation::Run(parse_command(args)?)),
           "child" => {
               let cgroup = PathBuf::from(args.next()?);
               Some(Invocation::Child {
                   cgroup,
                   command: parse_command(args)?,
               })
           }
           _ => None,
       }
   }
   ```

   Debajo de `parse`, con una línea en blanco, la función que lee el programa y sus argumentos. Antes estaba dentro de `parse`:

   ```rust title="src/cli.rs" ins={1-7}
   fn parse_command(mut args: impl Iterator<Item = String>) -> Option<CommandLine> {
       let program = args.next()?;
       Some(CommandLine {
           program,
           args: args.collect(),
       })
   }
   ```

   - `match args.next()?.as_str()`: la primera palabra decide: `run` o `child`. Cualquier otra sale por `_ => None`.
   - `"run" => Some(Invocation::Run(parse_command(args)?))`: lee el programa y los argumentos con `parse_command`. Si falta el programa, el `?` devuelve `None`.
   - `"child" => { ... }`: primero la ruta del cgroup: `PathBuf::from(args.next()?)` toma la primera palabra que queda y la hace ruta. Después, `parse_command` lee lo demás.
   - `parse_command(mut args: impl Iterator<Item = String>)`: recibe el resto de las palabras. El `mut` es porque `next` las va gastando. Devuelve el `CommandLine`, o `None` si no queda ni el programa.
   - `args: args.collect()`: las palabras que sobran, los argumentos del programa.
   - Con una palabra desconocida, con `child` y solo la ruta, o con `run` sin programa, `parse` devuelve `None`, y `main` imprime el uso.

8. **El hijo necesita su propia copia de montajes: `namespaces.rs`.**

Tu programa, el padre, pidió la suya con `unshare_namespaces`, y el hijo, que nace después, la hereda: **comparten la misma**.

La raíz vieja es la de tu máquina. Dicho en español: cambia la raíz de cada proceso de esa copia de montajes que apunte a la raíz vieja.

## Salir sin dejar nada

## Resumen

| Situación | Qué usar |
| --- | --- |
| Quieres que el comando no pase de cierta cantidad de RAM | Un cgroup: `Cgroup::create(...)` y `limit_memory(MEMORY_MAX)`, que escribe `memory.max` y pone `memory.swap.max` en `0` |
| Quieres que el comando viva dentro del cgroup | `cgroup::join(cgroup)` en el hijo, lo primero de `init` y antes de `enter_rootfs` |
| Quieres saber si el kernel mató algo | `oom_kills()`, que lee `oom_kill` en `memory.events`, y un aviso por stderr si es mayor que 0 |
| Quieres que la carpeta se borre sola, también con un error | `impl Drop for Cgroup`, y terminar `run` devolviendo `ExitCode`, no con `std::process::exit` |
| El padre no encuentra `/sys/fs/cgroup` después de que el hijo cambia de raíz | `namespaces::unshare_mounts()` en `init`, para que el hijo tenga su propia copia de montajes |
| Quedó una carpeta `mini-container-*` de más | **Destructivo:** `sudo rmdir /sys/fs/cgroup/mini-container-*` |

### 3a.1 Frena la CPU en vez de matar

**Objetivo:** limita el comando a medio núcleo de CPU y mide qué le pasa cuando quiere más. Un núcleo es una unidad de la CPU que ejecuta un programa a la vez.

En la lección te quedó una pregunta: «A llega a su límite de medio núcleo de CPU y quiere más. ¿El kernel lo mata, como hace con la RAM, o hace otra cosa?». Es también la pregunta de cómo limita Docker la CPU. Hoy la contestas midiendo.

La CPU se limita con otro archivo del cgroup: `cpu.max`. Lleva dos números separados por un espacio: cuántos microsegundos de CPU puede gastar el cgroup en cada periodo, y cuánto dura el periodo. Un microsegundo es una millonésima de segundo. Con `50000 100000`, el cgroup gasta hasta 50 000 microsegundos de cada 100 000: medio núcleo. Según la documentación de Docker, `docker run --cpus=0.5` equivale a `--cpu-period=100000` y `--cpu-quota=50000`: la misma cuota y el mismo periodo.

Mira lo que pasa hoy. El comando es un bucle que gasta CPU durante 5 segundos. Lo lanzas en segundo plano, esperas 6 segundos y lees el cgroup, que sigue vivo porque el comando duerme 5 segundos más:

```sh title="Antes"
$ sudo ./target/debug/mini-container run /bin/sh -c 'timeout 5 yes > /dev/null; sleep 5' & sleep 6; cat /sys/fs/cgroup/mini-container-*/cpu.max /sys/fs/cgroup/mini-container-*/cpu.stat; wait
[1] 68496
Terminated
max 100000
usage_usec 5051913
user_usec 4937915
system_usec 113998
nice_usec 0
nr_periods 0
nr_throttled 0
throttled_usec 0
nr_bursts 0
burst_usec 0
```

- `sudo ./target/debug/mini-container run /bin/sh -c '...'`: lanza `sh` dentro del contenedor con la orden entre comillas simples.
- `timeout 5 yes > /dev/null`: `yes` repite la letra `y` sin parar, y eso gasta CPU todo el tiempo. `> /dev/null` tira lo que imprime. `timeout 5` lo detiene a los 5 segundos.
- `; sleep 5`: duerme 5 segundos más. El cgroup sigue vivo. Sin esto, se borraría al terminar el bucle y no podrías leerlo.
- `&` al final del comando: lo manda a segundo plano, y tu <Term id="terminal">terminal</Term> queda libre. Una terminal interactiva puede imprimir `[1] 68496`: el número del trabajo y el PID. Es un aviso de la terminal, no de tu programa.
- `sleep 6`: espera 6 segundos. El bucle ya terminó, y el contenedor todavía duerme.
- `cat /sys/fs/cgroup/mini-container-*/cpu.max /sys/fs/cgroup/mini-container-*/cpu.stat`: imprime los dos archivos. `*` es el número de tu programa en esa ejecución.
- `wait`: espera a que el contenedor termine.
- Efecto: ninguno fuera de los 10 segundos que dura el contenedor.
- `Terminated`: lo imprime el `sh` de Alpine cuando `timeout` detiene a `yes`.
- `max 100000`: `cpu.max` sin tope. `max` es «sin límite» y el segundo número es el periodo.
- `usage_usec 5051913`: la CPU que gastó el cgroup, en microsegundos: unos 5 segundos, un núcleo entero durante 5 segundos.
- `nr_throttled 0`: ninguna vez frenado. Los demás números cambian en cada ejecución.

El resultado esperado, con el mismo comando, es otro:

```sh title="Resultado esperado"
$ sudo ./target/debug/mini-container run /bin/sh -c 'timeout 5 yes > /dev/null; sleep 5' & sleep 6; cat /sys/fs/cgroup/mini-container-*/cpu.max /sys/fs/cgroup/mini-container-*/cpu.stat; wait
[1] 68476
Terminated
50000 100000
usage_usec 2542754
user_usec 2500127
system_usec 42627
nice_usec 0
nr_periods 53
nr_throttled 50
throttled_usec 2500906
nr_bursts 0
burst_usec 0
```

- `50000 100000`: lo que escribiste en `cpu.max`.
- `usage_usec 2542754`: la CPU gastada, unos 2,5 segundos: la mitad que antes.
- `nr_periods 53`: los periodos de 100 milisegundos que pasaron.
- `nr_throttled 50`: las veces que el kernel frenó al comando. Es el número que importa: tiene que ser mayor que 0, y cerca de 50. Un comando frenado no puede seguir hasta el periodo siguiente.
- `throttled_usec 2500906`: el tiempo que pasó frenado, unos 2,5 segundos.

Con eso respondes la pregunta de la lección: con la CPU, el kernel no mata. Frena. En cada periodo de 100 milisegundos deja gastar 50 milisegundos y deja parado al comando el resto. El comando sigue vivo y termina lo suyo, más despacio. Docker hace lo mismo con `--cpus`: escribe `cpu.max` en el cgroup del contenedor.

Tu cambio queda en `src/cgroup.rs` y `src/container.rs`. La prueba de 3a sigue dando `OK`.

## Fuentes

- Documentación de cgroup v2 del kernel. `memory.max`: «Memory usage hard limit. This is the main mechanism to limit memory usage of a cgroup. If a cgroup's memory usage reaches this limit and can't be reduced, the OOM killer is invoked in the cgroup.» `memory.swap.max`: «Swap usage hard limit. If a cgroup's swap usage reaches this limit, anonymous memory of the cgroup will not be swapped out.» `memory.events`: «oom_kill: The number of processes belonging to this cgroup killed by any kind of OOM killer.» `memory.oom.group`: «If the OOM killer is invoked in a cgroup, it's not going to kill any tasks outside of this cgroup». `cgroup.procs`: «A PID can be written to migrate the process associated with the PID to the cgroup». Un cgroup se crea con `mkdir`, y «A cgroup which doesn't have any children or live processes can be destroyed by removing the directory». `cpu.max`: formato `$MAX $PERIOD`, «which indicates that the group may consume up to $MAX in each $PERIOD duration», con «max 100000» por defecto. `/proc/$PID/cgroup`: la entrada de cgroup v2 «is always in the format "0::$PATH"». [docs.kernel.org/admin-guide/cgroup-v2.html](https://docs.kernel.org/admin-guide/cgroup-v2.html). Consultada el 2026-11-13.
- Documentación de CFS Bandwidth Control del kernel: «Within each given "period" (microseconds), a task group is allocated up to "quota" microseconds of CPU time», y «Throttled threads will not be able to run again until the next period when the quota is replenished». Estadísticas de `cpu.stat`: `nr_periods` es «Number of enforcement intervals that have elapsed», `nr_throttled` es «Number of times the group has been throttled/limited». [docs.kernel.org/scheduler/sched-bwc.html](https://docs.kernel.org/scheduler/sched-bwc.html). Consultada el 2026-11-13.
- Documentación de Docker, «Resource constraints». `--cpus`: «This is the equivalent of setting --cpu-period="100000" and --cpu-quota="150000"» para `--cpus="1.5"`.
