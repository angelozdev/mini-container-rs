**Al terminar:** tu programa lanza `/bin/sh`, espera a que termine y devuelve el mismo <Term id="exit-code">código de salida</Term> que el <Term id="shell">shell</Term>.

Todavía no hay aislamiento. Este paso construye la base: un programa que lanza a otro y le cuenta a tu <Term id="terminal">terminal</Term> cómo le fue.

El <Term id="kernel">kernel</Term> es el núcleo de Linux: el programa que reparte la máquina entre todos los <Term id="process">procesos</Term>. Un *proceso* es un programa en ejecución. Un *shell* es un programa que lee comandos y los ejecuta, y `/bin/sh` es el shell básico de Linux. Hoy tu programa solo agrega un eslabón entre la terminal y el shell.

<Aside type="note" title="Analogía">
Tu programa es un jefe de obra. Manda a un albañil, el shell, a hacer un trabajo y se queda esperando. Cuando el albañil termina, le dice con un número cómo le fue: 0 es «bien» y cualquier otro número es «hubo un problema». El jefe repite ese número a quien lo contrató, que es tu terminal.
</Aside>

## Qué vas a escribir

Tres archivos, de lo más pequeño a lo que los junta:

1. `src/cli.rs` lee lo que escribiste en la terminal.
2. `src/container.rs` lanza el programa y espera.
3. `src/main.rs` conecta los dos.

Los archivos se escriben en el Mac, con Zed, dentro de `/Users/tu-usuario/mini-container-rs`. Los comandos de `cargo` y de `sudo` se corren en Linux. La máquina Linux ve la misma carpeta, así que lo que guardas en Zed ya está allí.

Todo el código va en inglés, también los textos que el programa imprime. La página te explica en español qué dice cada texto la primera vez que aparece.

Teclea cada trozo. No lo copies: el que teclea lee cada línea, y el que copia no.

Una última cosa antes de la predicción. Cuando un programa termina, deja un número: su *código de salida*. `0` significa «todo salió bien». Cualquier otro número significa «hubo un problema». Tu shell guarda el código del último comando en `$?`, y `echo $?` lo imprime. `echo` escribe en pantalla lo que le des.

2. **Describe lo que el usuario escribe: `src/cli.rs`.**

   En Zed, crea el archivo `src/cli.rs`. Primero, los tipos y el mensaje de uso:

   ```rust title="src/cli.rs"
   #[derive(Debug, PartialEq, Eq)]
   pub struct CommandLine {
       pub program: String,
       pub args: Vec<String>,
   }

   #[derive(Debug, PartialEq, Eq)]
   pub enum Invocation {
       Run(CommandLine),
   }

   pub const USAGE: &str = "usage: mini-container run <program> [args...]";
   ```

   - `pub struct CommandLine`: un `struct` junta varios datos con nombre en un solo valor. `pub` lo deja ver desde otros archivos.
   - `program: String`: el programa que hay que lanzar, por ejemplo `/bin/sh`. Un `String` es texto que le pertenece al `struct`.
   - `args: Vec<String>`: los argumentos de ese programa. Un `Vec` es una lista que puede crecer.
   - `pub enum Invocation`: un `enum` es un valor que es una de varias opciones. Hoy hay una sola, `Run`. Con un `enum` ya queda el sitio para añadir más sin cambiar el resto.
   - `Run(CommandLine)`: la opción `Run` trae dentro una `CommandLine`.
   - `pub const USAGE`: un texto fijo que se imprimirá cuando alguien use mal el programa. `&str` es un texto prestado que dura todo el programa.
   - El texto dice, en español: `uso: mini-container run <programa> [argumentos...]`. Lo que va entre `<>` es obligatorio, y lo que va entre `[]` es opcional.

   Las líneas `#[derive(...)]` merecen su propia explicación. Una línea `#[...]` encima de un tipo es un <Term id="attribute">atributo</Term>: una instrucción para el compilador. `derive` le pide a Rust que escriba por ti el código de ciertos <Term id="trait">traits</Term>. Un *trait* es una capacidad que un tipo puede tener.

   - `Debug`: el tipo se puede imprimir para depurarlo, es decir, para ver su contenido cuando buscas un fallo. Un texto de Rust puede llevar <Term id="placeholder">huecos</Term>, que son `{}` que Rust rellena con un valor. El hueco `{:?}` pide esa forma de imprimir. Tu programa todavía no lo usa: en el paso 4 verás un hueco simple, `{}`.
   - `PartialEq`: dos valores del tipo se pueden comparar con `==`.
   - `Eq`: promete que un valor siempre es igual a sí mismo. `String` y `Vec` lo cumplen. Un número decimal no, por el valor `NaN`. `Eq` solo se puede derivar junto con `PartialEq`.

   Tu programa todavía no usa estas capacidades. Las pones ahora porque en Rust un tipo público casi siempre las lleva: las guías de la API de Rust piden `Debug` en todos los tipos públicos y los traits comunes en los tipos nuevos.

   Ahora la función que lee los argumentos. Añade las líneas nuevas debajo de `USAGE`:

   ```rust title="src/cli.rs" ins={13-26}
   #[derive(Debug, PartialEq, Eq)]
   pub struct CommandLine {
       pub program: String,
       pub args: Vec<String>,
   }

   #[derive(Debug, PartialEq, Eq)]
   pub enum Invocation {
       Run(CommandLine),
   }

   pub const USAGE: &str = "usage: mini-container run <program> [args...]";

   pub fn parse(args: impl IntoIterator<Item = String>) -> Option<Invocation> {
       let mut args = args.into_iter();
       match args.next()?.as_str() {
           "run" => {
               let program = args.next()?;
               Some(Invocation::Run(CommandLine {
                   program,
                   args: args.collect(),
               }))
           }
           _ => None,
       }
   }
   ```

   - `args: impl IntoIterator<Item = String>`: acepta cualquier cosa que se pueda recorrer entregando `String`. Desde `main` le pasaremos los argumentos de la terminal.
   - `-> Option<Invocation>`: un `Option` es un valor que puede faltar: `Some(valor)` o `None`. Aquí `None` significa «no entendí los argumentos».
   - `let mut args = args.into_iter();`: convierte los argumentos en algo del que puedes sacar un elemento a la vez. `mut` porque sacar un elemento lo cambia.
   - `args.next()?`: saca el siguiente elemento. Si no hay ninguno, el `?` sale de la función devolviendo `None`.
   - `.as_str()`: presta ese `String` como texto, para compararlo con `"run"`.
   - `match ... { ... }`: un `match` compara un valor con una lista de opciones, de arriba abajo, y corre la primera que coincide. Cada línea `opción => resultado` se llama <Term id="arm">brazo</Term>.
   - `"run" => { ... }`: el primer brazo. Si la primera palabra es `run`, sigue por aquí.
   - `let program = args.next()?;`: la segunda palabra es el programa. Si falta, el `?` devuelve `None`: `run` sin programa no sirve.
   - `args: args.collect()`: junta todo lo que queda en un `Vec<String>`. Esos son los argumentos del programa.
   - `program,` solo, sin `program: program`: Rust lo permite cuando el campo y la variable se llaman igual.
   - `_ => None`: el guion bajo significa «cualquier otro valor». Cualquier otra primera palabra no se entiende.

3. **Lanza el programa y espera: `src/container.rs`.**

   En Zed, crea `src/container.rs`. Empieza por lo que el archivo necesita traer:

   ```rust title="src/container.rs"
   use std::os::unix::process::ExitStatusExt;
   use std::process::{Command, ExitCode, ExitStatus};

   use anyhow::{Context, Result};

   use crate::cli::CommandLine;
   ```

   - `use ...`: trae un nombre de otro lugar para usarlo sin escribir la ruta completa.
   - `ExitStatusExt`: añade el método `.signal()` al tipo `ExitStatus`. Solo existe en Unix, la familia de Linux y macOS.
   - `Command`: arma y lanza otro programa.
   - `ExitCode`: el número que un programa devuelve a quien lo lanzó cuando termina.
   - `ExitStatus`: cómo terminó un programa hijo.
   - `Context` y `Result` de `anyhow`: `Result` es el resultado de algo que puede fallar, `Ok(valor)` o `Err(error)`. `Context` permite añadir un mensaje al error.
   - `crate::cli::CommandLine`: `crate` es tu proyecto. Trae el `struct` que escribiste en `cli.rs`.

   Ahora la función que lanza el programa:

   ```rust title="src/container.rs" ins={7-14}
   use std::os::unix::process::ExitStatusExt;
   use std::process::{Command, ExitCode, ExitStatus};

   use anyhow::{Context, Result};

   use crate::cli::CommandLine;

   pub fn run(command: &CommandLine) -> Result<ExitCode> {
       let status = Command::new(&command.program)
           .args(&command.args)
           .status()
           .context("could not launch the program")?;
       Ok(ExitCode::from(exit_code(status)))
   }
   ```

   - `command: &CommandLine`: el `&` presta la `CommandLine` para leerla sin quedártela.
   - `-> Result<ExitCode>`: devuelve `Ok(ExitCode)` si todo fue bien o `Err` si algo falló.
   - `Command::new(&command.program)`: prepara el lanzamiento de ese programa.
   - `.args(&command.args)`: le añade sus argumentos.
   - `.status()`: lo lanza, espera a que termine y entrega su `ExitStatus`. Falla si el programa no se pudo lanzar, por ejemplo porque no existe.
   - `.context("could not launch the program")`: si hubo un fallo, le pone este mensaje por delante. Dice «no pude lanzar el programa». El error original queda como la causa.
   - `?`: si hubo un error, sale de `run` devolviéndolo. Si no, sigue con el valor.
   - `Ok(ExitCode::from(exit_code(status)))`: `exit_code` es la función que escribes a continuación. Convierte el estado en un número, `ExitCode::from` lo vuelve un `ExitCode` y `Ok(...)` lo envuelve.

   Antes de escribir `exit_code`, hay que saber cómo termina un proceso. Hay dos maneras.

   La primera: el proceso llama a `exit(código)`. Entonces deja un código de salida, de 0 a 255.

   La segunda: el proceso recibe una <Term id="signal">señal</Term> que lo mata. Una señal es un aviso que el kernel le manda a un proceso. La señal 9, llamada `SIGKILL`, lo mata en el acto, y el proceso no puede evitarlo. Entonces no hay código de salida: solo queda el número de la señal.

   `status.code()` es el método de `ExitStatus` que pregunta por el código de salida. Devuelve un `Option`: `Some(código)` si el proceso llamó a `exit`, y `None` si no hay código.

   <Quiz kind="prediction">
   <Fragment slot="question">Un shell corre `kill -9 $$`. Ese comando le manda al propio shell la señal 9: `kill` manda una señal, `-9` es el número y `$$` es el número de proceso del shell. El shell no llega a llamar a `exit`. ¿Qué devuelve `status.code()` para ese hijo?</Fragment>

   <QuizOption>`Some(9)`.<Fragment slot="feedback">El 9 es el número de la señal, no un código de salida. Un código de salida solo existe si el proceso termina llamando a `exit`.</Fragment></QuizOption>

   <QuizOption correct>`None`.<Fragment slot="feedback">Murió por una señal, así que no hay código de salida. El kernel guarda las dos cosas por separado: el código, si hubo, y el número de la señal, si hubo.</Fragment></QuizOption>

   <QuizOption>`Some(137)`.<Fragment slot="feedback">El 137 lo calcula tu programa, no el kernel. El kernel no inventa un código cuando la causa fue una señal.</Fragment></QuizOption>
   </Quiz>

   Falta la función que convierte el estado en un número:

   ```rust title="src/container.rs" ins={15-23}
   use std::os::unix::process::ExitStatusExt;
   use std::process::{Command, ExitCode, ExitStatus};

   use anyhow::{Context, Result};

   use crate::cli::CommandLine;

   pub fn run(command: &CommandLine) -> Result<ExitCode> {
       let status = Command::new(&command.program)
           .args(&command.args)
           .status()
           .context("could not launch the program")?;
       Ok(ExitCode::from(exit_code(status)))
   }

   fn exit_code(status: ExitStatus) -> u8 {
       const SIGNAL_EXIT_BASE: u8 = 128;

       match status.code() {
           Some(code) => code as u8,
           None => SIGNAL_EXIT_BASE + status.signal().unwrap_or_default() as u8,
       }
   }
   ```

   - `fn exit_code`: sin `pub`, solo se usa dentro de este archivo.
   - `-> u8`: un número de 0 a 255, que es lo que cabe en un código de salida.
   - `const SIGNAL_EXIT_BASE: u8 = 128;`: un nombre para el 128, para que no sea un número suelto. Lo explico en la sección «Por qué 128 + señal».
   - `match status.code()`: otro `match`. Esta vez compara el `Option` con sus dos formas.
   - `Some(code) => code as u8`: el hijo llamó a `exit`. `as u8` convierte el número a `u8`. Cabe porque un código de salida tiene 8 bits.
   - `None => ...`: aquí lo mató una señal. `status.signal()` entrega el número de la señal, y por eso hacía falta `ExitStatusExt`.
   - `.unwrap_or_default()`: si no hubiera señal, usa 0. En este caso no puede pasar. No usamos `.unwrap()` porque haría que el programa se cayera con un `panic` si el valor faltara.

4. **Júntalo todo: `src/main.rs`.**

   Tu `main.rs` tiene ahora los dos `mod` y el «hola mundo» que escribió `cargo init`. Añade, debajo de los `mod`, lo que `main` necesita traer:

   ```rust title="src/main.rs" ins={4-5}
   mod cli;
   mod container;

   use std::env;
   use std::process::ExitCode;
   ```

   - `use std::env;`: `env` da acceso a lo que rodea al programa, como sus argumentos.
   - `use std::process::ExitCode;`: el mismo `ExitCode` de antes.

   Ahora reemplaza el `fn main` de ejemplo por el tuyo:

   ```rust title="src/main.rs" del={7-9} ins={10-18}
   mod cli;
   mod container;

   use std::env;
   use std::process::ExitCode;

   fn main() {
       println!("Hello, world!");
   }
   fn main() -> anyhow::Result<ExitCode> {
       match cli::parse(env::args().skip(1)) {
           Some(cli::Invocation::Run(command)) => container::run(&command),
           None => {
               eprintln!("{}", cli::USAGE);
               Ok(ExitCode::from(2))
           }
       }
   }
   ```

   - `fn main() -> anyhow::Result<ExitCode>`: `main` puede devolver un `Result`. Si devuelve `Err`, Rust imprime `Error: ...` por <Term id="stderr">stderr</Term> y sale con el código 1. *stderr* es el canal por donde un programa escribe sus errores. El otro canal, <Term id="stdout">stdout</Term>, es para su salida normal. Así un aviso no se mezcla con lo que el programa produce.
   - `env::args()`: las palabras que escribiste en la terminal. La primera es la ruta del propio programa.
   - `.skip(1)`: se salta esa primera palabra, que a `parse` no le sirve.
   - `match cli::parse(...)`: el tercer `match`. Compara lo que devuelve `parse` con dos opciones.
   - `Some(cli::Invocation::Run(command)) => container::run(&command)`: si `parse` entendió un `run`, lanza el programa.
   - `None => { ... }`: si no entendió, imprime el uso y sale con el código 2.
   - `eprintln!`: imprime una línea por stderr, no por stdout. La salida normal del programa queda libre.
   - El `!` al final de `eprintln!` marca una <Term id="macro">macro</Term>: código que Rust expande mientras compila.
   - `"{}"`: la plantilla de `eprintln!`, con un solo hueco `{}`. Rust lo rellena con el valor que sigue, aquí `cli::USAGE`. Hace falta la plantilla porque Rust exige que el primer argumento sea un texto escrito a mano, no una constante.
   - El 2 es nuestra elección: separa «me usaron mal» (2) de «falló al ejecutar» (1).

## Corre tu programa

Compilas siempre como tu usuario, con `cargo build`. Y corres el binario con `sudo`. Corre tu programa en Linux:

```sh title="En Linux"
sudo ./target/debug/mini-container run /bin/echo hello
```

- `sudo`: corre el comando como administrador. En este paso todavía no hace falta. Lo usamos ya para no cambiar el comando cuando lo pida el aislamiento.
- `./target/debug/mini-container`: la ruta de tu binario. El `.` es la carpeta actual. Como la ruta lleva `/`, `sudo` la usa tal cual y no la busca en el `PATH`.
- `run`: la palabra que `parse` espera primero.
- `/bin/echo hello`: el programa que se lanza y su argumento.
- Efecto: tu programa lanza `echo`, espera a que termine y sale con su código.

<ShouldSee>

```sh title="Deberías ver"
$ sudo ./target/debug/mini-container run /bin/echo hello
hello
```

</ShouldSee>

Ahora el código de salida:

```sh title="En Linux"
sudo ./target/debug/mini-container run /bin/sh -c 'exit 3'; echo $?
```

- `/bin/sh -c 'exit 3'`: lanza un shell con `-c`, que le dice «ejecuta este texto». El texto, `exit 3`, termina el shell con el código 3.
- Las comillas simples evitan que tu shell toque el texto antes de pasárselo a `sh`.
- `;`: separa dos comandos. El segundo corre cuando el primero termina.
- `echo $?`: imprime el código de salida del comando anterior.

<ShouldSee>

```sh title="Deberías ver"
$ sudo ./target/debug/mini-container run /bin/sh -c 'exit 3'; echo $?

```

## Por qué 128 + señal

Los shells quieren un solo número para todo. Por eso usan una convención: si el proceso murió por la señal N, el código es 128 + N. Con la señal 9 queda 128 + 9 = 137. Tu programa copia esa convención en `exit_code`.

Compruébalo:

```sh title="En Linux"
sudo ./target/debug/mini-container run /bin/sh -c 'kill -9 $$'; echo $?
```

- `kill -9 $$`: `kill` manda una señal. `-9` es el número de la señal. `$$` es el número de proceso, el <Term id="pid">PID</Term>, del shell que lo ejecuta. El shell se mata a sí mismo.
- Las comillas simples son obligatorias. Con comillas dobles, tu shell cambiaría `$$` por su propio PID antes de lanzar nada, y el `kill` mataría a tu terminal en vez de al hijo.
- `; echo $?`: imprime el código de salida del comando anterior.

<ShouldSee>

```sh title="Deberías ver"
$ sudo ./target/debug/mini-container run /bin/sh -c 'kill -9 $$'; echo $?
137
```

</ShouldSee>

Un código de salida tiene solo 8 bits. Un proceso que llama a `exit(256)` devuelve 0, porque solo se guarda el byte bajo del número.

## Cuando el programa no existe

Prueba con un nombre mal escrito:

```sh title="En Linux"
sudo ./target/debug/mini-container run holaa; echo $?
```

- `run holaa`: pide lanzar un programa llamado `holaa`, que no existe.
- `; echo $?`: imprime el código de salida del comando anterior.
- Efecto: `.status()` falla y `run` devuelve el error con el mensaje que le pusiste.

<ShouldSee>

```sh title="Deberías ver" stderr={2-5}
$ sudo ./target/debug/mini-container run holaa; echo $?
Error: could not launch the program

Caused by:
    No such file or directory (os error 2)
1
```

</ShouldSee>

- `Error: could not launch the program`: es el mensaje que pusiste con `.context(...)`. Dice «no pude lanzar el programa». `main` añade el `Error:` por delante.
- `Caused by:`: significa «causado por». Introduce la causa, el error original que dio el sistema.
- `No such file or directory (os error 2)`: «no existe el archivo o directorio». El 2 es el código de error del sistema para eso.
- El último `1` es el código de salida de tu programa.

El mensaje no dice qué programa falló. Lo arreglas en el ejercicio.

Con un programa que existe y con uno que no, viste las dos salidas de `.status()`:

  okNote="el programa corrió y terminó"
  error="Err(error)"
  errorNote="no se pudo lanzar: sale con 1"
/>

## Resumen

| Situación | Qué usar |
| --- | --- |
| Quieres lanzar otro programa y esperar a que termine | `Command::new(&command.program).args(&command.args).status()` |
| Quieres saber cómo terminó el hijo | `status.code()`: `Some(código)` si llamó a `exit`, `None` si lo mató una señal |
| Una señal mató al hijo y tu programa debe devolver un código | `128` más el número de la señal: con `kill -9` sale `137` |
| Una llamada puede fallar y quieres decir qué intentaba tu programa | `.context("…")` y `?` |
| Te usaron mal: falta `run` o el programa | `eprintln!("{}", cli::USAGE)` y salir con el código `2` |
| Cambiaste el código y el resultado no cambia | `cargo build` antes de correr el binario |

### 1a.1 Que el error diga qué programa no existe
